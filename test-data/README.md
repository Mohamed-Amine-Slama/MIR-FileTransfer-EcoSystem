# test-data — SYNTHETIC DICOM ONLY

> **ADR-7: real patient data never leaves production.**
> Nothing in this directory may ever be derived from a real patient. Not for a
> bug reproduction, not "just this once", not with the name blanked out.
> De-identification is not a substitute — pixel data can carry burned-in
> identifiers and private tags routinely carry more.

Every file here is generated byte-by-byte by `generate-fixtures.mjs`. No file
was downloaded from a clinical source or exported from a scanner.

## Regenerating

```bash
node test-data/generate-fixtures.mjs   # rewrites test-data/dicom/ from scratch
node test-data/check-synthetic.mjs     # CI guard — must exit 0
```

The output is deterministic: the same bytes on every run, on every machine.
Fixtures are committed so CI needs neither network access nor a generation step.

## Why generated instead of downloaded

P0.2 suggests downloading TCIA / NCI Imaging Data Commons or Orthanc sample
files. We generate instead, for three reasons:

1. A generated corpus **cannot** contain real patient data, even by accident.
   A downloaded one relies on someone else's de-identification being correct.
2. CI needs no network access, and the bytes never drift under us.
3. P6.1 requires deliberately malformed inputs — corrupt, non-DICOM, missing
   preamble, lossy-encoded — that no public clinical dataset ships.

All UIDs use the root `1.3.6.1.4.1.99999.1`, which is deliberately **not** a
registered OID arc. Any UID from this corpus is recognisable as fake on sight
and can never collide with a real study.

Fixtures 1–5 are the five required by the P0.2 gate. Fixtures 6 and 7 are
additions required to test P6.1 properly; the spec's five do not cover them.

### Expected behaviour (P6.1 contract)

| Fixture | `isDicom()` | `readHeader()` | Notes |
|---|---|---|---|
| 01 single CT | ✅ true | ✅ parses | modality `CT` |
| 02 CT series | ✅ true (×120) | ✅ parses (×120) | 1 study UID, 120 distinct SOP UIDs |
| 03 MR series | ✅ true (×24) | ✅ parses | modality `MR` |
| 04 corrupt | ✅ **true** | ❌ throws | See below |
| 05 not-DICOM | ❌ false | not attempted | Rejected on magic bytes |
| 06 lossy | ✅ true | ✅ parses | `isLossyTransferSyntax` → **true**; flag, do not reject |
| 07 no-preamble | ❌ false | not attempted | Rejected, logged as `rejected_no_preamble` |

**Fixture 04 is the important one.** It has a valid 128-byte preamble and valid
`DICM` magic, so it *passes* the magic-byte check and *fails* at parse time. A
validator that only checks magic bytes will wave it through. That is exactly the
failure P6.1's "rejected with a specific error" requirement exists to catch — the
two rejection reasons are not interchangeable and must be reported distinctly.

**Fixture 07 exists to be measured, not just rejected.** Some legacy scanners
emit DICOM without the preamble. P6.1 rejects these, but logs them under a
distinct `rejected_no_preamble` reason so we can find out whether real Libyan
clinics actually hit this before deciding whether to loosen the rule. Loosening
it blind would weaken the only cheap format check we have.

### Deliberately not normalised

- The CT series (fixture 02) is written **extensionless** (`IM000001`, …). Real
  clinic CDs frequently ship files with no extension, often under a `DICOM/` or
  `IMAGES/` folder. P7.3's folder upload has to cope with this, so the fixture
  reflects it rather than hiding it behind a tidy `.dcm` suffix.
- `PatientName` values in these files are **not** authoritative for record
  linkage and must never be used as such (P6.1 rule). They exist so the
  synthetic-data guard has something to assert on.

## The CI guard

`check-synthetic.mjs` fails the build if any `PatientName` under `test-data/`
does not match `/^SYNTHETIC\^[A-Z0-9]+\^*$/`.

It is an **allowlist**, not a denylist of real-looking names. A denylist only
catches names someone thought to enumerate. An allowlist fails closed on
anything unexpected — the correct posture when the failure being guarded against
is "real patient data reached the repository".

The guard also fails if it scans files but finds **zero** PatientName tags. A
guard that silently inspects nothing reports success forever; that is worse than
no guard, because it is trusted.
